# 美容医療LP AI生成システム 設計レポート

> 本レポートは、美容クリニック・美容系商材のLP制作を「AIを活用して仕組み化」するためのシステム設計をまとめたものである。ゴールは、デザイナー以外のメンバーでも「クライアント要件・キャンペーン内容・競合LP」等を入力すれば、一定水準以上のクオリティのLPが出力される状態を、プロンプト化・スキル化して実現することにある。

---

## 0. 結論（サマリー）

本システムは、LP制作という属人的な工程を **3層のパイプライン**（入力 → 生成 → 品質保証）に分解し、各工程を「機械が決定論的に判定できる作業」と「人が責任を負って判断すべき作業」に切り分けて再設計するものである。

- 運用メンバー（非デザイナー）が触るのは **入力シートを埋める** ことと **チェックシートで確認する** ことの2点のみ。
- デザイン・コピー・コーディングといった「作る」工程は全てAIが自動で実行する。
- 薬機法・医療広告ガイドライン、実写素材、ブランド判断といった「間違うと事故る」工程だけを、意図的に自動化から切り離し人間の確認に残す。

この「自動化する部分」と「人が確認する部分」の境界を明文化して固定することが、非デザイナー運用でも品質の下限を割らせないための核心である。

---

## 1. システムアーキテクチャ

全体は3層構造で構成する。各層の境界には必ず **スキーマ検証（型チェック）** を挟み、前工程の出力が次工程の想定形式を満たしていることを保証する。これにより、途中の工程が壊れても後続に不正なデータが流れ込まない。

```
┌─────────────┐   ┌──────────────────────────────┐   ┌──────────────────────┐
│  Intake層    │   │       Generation層            │   │       QA層            │
│ (構造化入力)  │──▶│      (AI生成パイプライン)       │──▶│ (自動チェック＋人間レビュー) │
└─────────────┘   └──────────────────────────────┘   └──────────────────────┘
 非デザイナーが操作      AIが自動実行（人は介在しない）         非デザイナーが確認 ＋ 監修者が承認
```

- **Intake層**：運用メンバーが構造化フォームに情報を入力する層。自由記述を極力排し、選択式・項目固定にすることで入力品質のばらつきを抑える。
- **Generation層**：AIが競合分析からコーディングまでを自動実行する層。人は介在しない。
- **QA層**：出力を検証する層。機械判定できるものは自動チェック（決定論）、責任を人が負うものは人間レビューに回す。

---

## 2. 処理フロー（全体像）

番号は工程IDを表す。①〜⑥がGeneration層、⑦⑧がQA層に対応する。

```
[Intake層]
  入力スキーマ（クライアント要件 / キャンペーン / 競合LP / 素材）
        │
        ├──────────────┬──────────────────┐
        ▼              ▼                  ▼
[Generation層]
  ① 競合LP分解      ② 要件正規化       ③ デザイントークン確定
  (RAG/構造抽出)    (自由記述→構造化)   (配色・余白・タイポ)
        │              │                  │
        └──────┬───────┴──────────────────┘
               ▼
        ④ 構成生成（ワイヤーフレーム / 構造JSON）
               ▼
        ⑤ コピー生成（＋ガードレール一次適用）
               ▼
        ⑥ コーディング（HTML / CSS / JS 出力）
               ▼
[QA層]
        ⑦ 自動QA（薬機法辞書 / 構造 / 技術チェック）
               ▼
        ⑧ 人間レビュー（監修 / 実素材 / ブランド判断）
               │
      ┌────────┴────────┐
   （OK）              （NG）
      ▼                  ▼
    公開          差分再生成ループ
                （該当セクションIDのみGeneration層へ戻す）
```

運用メンバーの操作は **入力スキーマを埋める（フロー起点）** と **⑧のチェックシートで確認する** の2点だけ。①〜⑦は全自動で走り、⑧の人間レビュー待ちでパイプラインが停止する設計とする。

## 3. Intake層 — 構造化入力

### 3.1 設計方針

非デザイナーが運用の起点になるため、入力は「自由に書く」のではなく「決められた項目を埋める」形式に固定する。自由記述はブレの温床になるため、可能な限り選択式（enum）にし、自由記述が必要な項目（顧客インサイト等）は後工程②で正規化する。

### 3.2 入力スキーマ

入力は以下の構造を持つJSONスキーマとして定義する。運用メンバーには、これをフォームUI（またはスプレッドシート）として提示する。

```jsonc
{
  "client": {
    "product_type": "enum[美容外科 | 美容皮膚科 | 脱毛 | 痩身 | 審美歯科 | AGA | ...]",
    "target": {
      "age_range": "例: 25-39",
      "gender": "enum[女性 | 男性 | 指定なし]",
      "insight": "顧客の悩み・動機（自由記述、②で正規化）"
    },
    "brand_tone": "enum[高級・上質 | クリニカル・信頼 | 親しみ・カジュアル | ...]",
    "regulatory_scope": "enum[医療広告 | 化粧品 | 医薬部外品]"
  },
  "campaign": {
    "offer": "訴求する特典・内容",
    "price": { "regular": 0, "campaign": 0, "unit": "円" },
    "deadline": "キャンペーン期限",
    "primary_cta": "enum[予約 | 資料請求 | LINE登録 | 無料カウンセリング]",
    "kpi": "このLPで最大化したい行動"
  },
  "competitors": ["https://competitor-1", "https://competitor-2", "https://competitor-3"],
  "assets": {
    "case_photos": ["症例写真URL/ファイル"],
    "logo": "ロゴファイル",
    "brand_colors": ["#000000"],
    "clinic_info": { "name": "医療機関名", "doctor": "医師名", "address": "..." }
  }
}
```

### 3.3 設計上の要点

`client.regulatory_scope`（適用される規制区分）の値が、QA層のチェックルールセットを自動分岐させるトリガーになる。

- `医療広告` → 医療広告ガイドラインの必須記載・禁止表現ルールを適用
- `化粧品 / 医薬部外品` → 薬機法（旧薬事法）の化粧品等表現規制ルールを適用

この分岐を入力段階で確定させておくことで、後工程のチェックが商材に対して過不足なく走る。

## 4. Generation層 — AI生成パイプライン

人が介在せず、AIが以下①〜⑥を順に自動実行する。各工程は中間成果物（構造化データ）を残し、後述する差分再生成を可能にする。

### ① 競合LP分解（RAG / 構造抽出）

入力された競合LPのURLを取得し、DOM構造とレンダリング結果から以下を抽出、正規化した中間表現（IR: Intermediate Representation）に変換する。

- **セクション構造**：ファーストビュー / 権威付け（医師・実績）/ 症例（Before・After）/ 料金・比較 / お客様の声 / FAQ / CTA帯 の出現順と繰り返しパターン
- **訴求の型**：症例数訴求・医師監修訴求・価格比較訴求・限定性訴求（期限・人数）のうち、どれを主軸に据えているか
- **デザイントークン**：主色 / 差し色 / CTA色の配色、タイポグラフィのスケール、余白のリズム、ファーストビューの視線導線設計

この工程の目的は競合を「模倣する」ことではなく、**業界で機能している構成の型を統計的に抽出し、後続のテンプレート選択とレイアウト設計の根拠にする** ことにある。

### ② 要件正規化

Intakeの自由記述部分（特に `target.insight`）をAIで解析し、生成プロンプトに渡せる構造化コンテキストへ変換する。曖昧な顧客要望を、訴求軸・トーン・優先順位という扱える形に落とす工程。

### ③ デザイントークン確定

①で抽出した業界標準トークンと、Intakeの `assets.brand_colors`（クライアント指定色）を突合し、最終的なデザイントークンを **CSS Custom Properties（CSS変数）** として確定する。

```css
:root {
  --color-primary: #...;    /* 主色 */
  --color-accent:  #...;    /* 差し色 */
  --color-cta:     #...;    /* CTAボタン色 */
  --space-unit:    8px;     /* 余白の基準単位 */
  --type-scale:    1.25;    /* タイポグラフィの比率 */
  --radius:        8px;
}
```

以降のコーディング（⑥）は、色・余白・フォントサイズを全てこのトークン参照で記述する。これにより、デザインの一貫性を「気をつける」ではなく **コード側の仕組みで強制** できる。

### ④ 構成生成（ワイヤーフレーム）

①のIRと②の要件から、セクション単位のワイヤーフレーム（構造JSON）を生成する。この段階ではレイアウトの骨格のみで、コピーもデザインも入れない。

```jsonc
{
  "sections": [
    { "id": "fv",       "type": "first_view",   "has_cta": true },
    { "id": "authority","type": "authority",    "content": "医師監修・実績" },
    { "id": "case",     "type": "before_after" },
    { "id": "price",    "type": "price_table",  "required_fields": ["費用", "リスク・副作用"] },
    { "id": "faq",      "type": "faq" },
    { "id": "cta_final","type": "cta_band",     "has_cta": true }
  ]
}
```

構造だけを先に確定させることで、コピーやデザインに入る前に「構成のレビュー」を独立して行える分離点になっている（必要に応じて④の段階で人間が構成だけ確認することも可能）。

### ⑤ コピー生成（＋ ガードレール一次適用）

④の各セクションに対しコピーを生成する。ここで **薬機法・医療広告のガードレールを一次適用** する。二段構えで検出する。

1. **決定論フィルタ（正規表現）**：「必ず治る」「絶対」「No.1」「最安」「即効」等、明確なNG表現を辞書との突合で機械的に検出・ブロックする。判定にブレがない。
2. **LLM分類器**：文脈依存のグレー表現（体験談の書き方、ビフォーアフター訴求の程度、効果の断定に近い言い回し等）を分類器でフラグ立てし、人間確認キュー（⑧）に積む。

ここでのガードレールは「一次フィルタ」であり、見逃しがある前提で設計する。最終判断は⑧の人間レビューが負う。

### ⑥ コーディング

④の構造・⑤のコピー・③のデザイントークンを統合し、実際のコードを出力する。

- **セマンティックHTML**：構造的に正しいマークアップ
- **CSS**：③のトークンを参照して記述（直値のハードコードを禁止し一貫性を担保）
- **最小限のJS**：CTA追従、FAQアコーディオン、フォーム挙動等
- レスポンシブ対応、計測タグ（GA/広告タグ）の挿入ポイント確保
- 実写素材が未確定の箇所は、寸法を固定したプレースホルダで埋める（後から素材を差し込むだけでレイアウトが崩れない）

## 5. QA層 — 自動チェック ＋ Human-in-the-loop

生成物を2段階で検証する。**機械判定できるものは全て自動化（⑦）し、責任を人が負うべきものだけを人間レビュー（⑧）に残す。** この切り分けが本システムの設計思想の中核である。

### ⑦ 自動QA（決定論・毎回必ず走る）

人の主観を介さず機械判定できる項目を全て自動チェックし、pass/fail のレポートを出力する。

- **薬機法 / 医療広告ガイドライン**
  - NG表現辞書との突合（誇大・断定・優良誤認表現の検出）
  - 必須記載事項の有無（医療機関名 / 医師名 / 自由診療である旨 / 費用 / リスク・副作用の明示 等）
  - ※適用ルールセットは Intake の `regulatory_scope` により自動分岐
- **構造チェック**
  - ファーストビュー内にCTAが存在するか
  - ファーストビューの高さ（離脱を招く過大でないか）
  - CTAの出現回数（少なすぎ / 多すぎの検出）
  - 料金表に必須項目が揃っているか
- **技術チェック**
  - HTML構文検証
  - Lighthouse（表示速度・アクセシビリティ・SEO の定量スコア）
  - リンク切れ検出
  - 計測タグの設置確認

### ⑧ 人間レビュー（"任せると事故る"部分だけ）

自動化しきれない、あるいは責任を人が負うべき項目だけをチェックシート化して残す。**意図的に自動化から切り離す** のがポイント。

| 確認項目 | 自動化しない理由 |
|---|---|
| 薬機法・医療広告の **最終監修** | ⑤・⑦は一次フィルタに過ぎない。最終的な適法性の判断は法的責任を伴うため、人（監修者）が負うべき領域。 |
| **症例写真・モデル・院内写真** | 実素材の適切性、および患者同意の取得済みか等は機械では判定不可能。 |
| ブランドとして越えてはいけない一線 | 定量化できない品質判断。チェックシートで基準を明文化し、担当者が変わっても同じ基準になるよう属人性を排除する。 |

### 5.1 修正ループ（差分再生成）

⑦または⑧でNGが出た場合、**該当セクションのIDと指摘内容だけ** をGeneration層に戻す。中間成果物（構造JSON・デザイントークン）が保存されているため、LP全体を作り直すのではなく、問題のあったセクションのみを差分再生成できる。

運用メンバーは指摘の言語化に悩む必要がなく、テンプレート化された指摘文（例：「このセクションのコピーが断定的すぎる」）から選ぶだけで修正指示が成立する。

## 6. 設計思想 — 自動化と人間確認の境界

本システムの一貫した原則は次の一文に集約される。

> **機械判定できるものは決定論に寄せて自動化し、責任を人が負うべきものだけを人間に残す。判断に迷うグレーゾーンは自動で通さず、必ず人間キューに積む（フェイルセーフ ＝ 迷ったら人間へ）。**

品質が崩れる仕組みは、たいてい「全部AIに任せた（＝規制違反や事故を素通し）」か「結局デザイナー頼み（＝仕組み化できていない）」のどちらかに陥る。本設計は最初から両者を分離し、境界を明文化して固定することでこれを回避する。

| 工程 | 判定方法 | 責任の所在 |
|---|---|---|
| ①〜⑥ 生成 | LLM ＋ テンプレート | システム（毎回ブレなく高速） |
| ⑤ ガードレール一次 | 正規表現 ＋ LLM分類器 | システム（一次フィルタ。見逃し前提で人間へ渡す） |
| ⑦ 自動QA | 決定論（辞書 / 構文 / Lighthouse） | システム（機械判定可能な範囲を網羅） |
| ⑧ 人間レビュー | チェックシート | **人間（法的責任・実素材・ブランド判断）** |

この境界線を曖昧にしないことが、非デザイナー運用でも品質の下限を割らせない最大の要因である。美容・医療系は特に規制が厳しく、ここを仕組みに組み込めるかどうかで成否が分かれる。

---

## 7. 納品物

1. **入力シート**：クライアント要件 / キャンペーン内容 / 競合LP / 素材（非デザイナーが埋める構造化フォーム）
2. **生成用プロンプト・スキル一式**：①〜⑧を1つの手続き（Skill）として定義したもの。美容医療特化・薬機法チェックを内蔵。
3. **公開前チェックシート**：誰が確認しても同じ基準になるよう明文化した⑧のレビュー項目。
4. **サンプルLP（実出力1本）**：上記の仕組みを使って実際に生成したLP。

---

## 8. 実装形態

- **プロンプト / SOPのスキル化**：①〜⑧を1つの手続き（Skill）として定義する。入力を渡すと⑧の直前まで自動で走り、人間レビュー待ちで停止する。運用メンバーは入力とチェックだけを担当する。
- **バージョン管理**：スキル・プロンプト・NG表現辞書・チェックシートをGitで管理し、医療広告ガイドラインや薬機法の改定に追従できるようにする。
- **再現性の担保**：同一入力に対する出力のブレを抑えるため、生成時のパラメータ（temperature）を工程別に固定する（構造生成＝低 / コピー生成＝中）。デザイントークンと構造JSONを中間成果物として保存し、コーディング以降を決定論的に再実行可能にする。
- **差分再生成**：修正はセクションID単位で行う。中間IRが残っているため、全体を作り直さず指摘箇所だけをGeneration層に戻せる。

## 9. 前提・スコープ（正直な線引き）

仕組みで担保できる範囲と、そうでない範囲を明確にしておく。

- **本システムが生成するもの**：構成 / レイアウト / コピーの叩き / 配色 / コーディング（HTML・CSS・JS）。
- **本システムが生成しないもの**：症例写真・モデル・院内写真などの **実写素材**。これらは差し込み前提で設計し、未確定時はプレースホルダで埋める。
- **人間が必ず担うもの**：薬機法・医療広告ガイドラインの **最終的な適法判断**（監修者の責任領域）。本システムは一次フィルタと必須記載チェックまでを自動化するが、最終承認は人間が行う。

この線引きを最初に明示しておくことこそが、美容・医療系という規制の厳しい領域で「仕組み化」を破綻させないための前提条件である。
